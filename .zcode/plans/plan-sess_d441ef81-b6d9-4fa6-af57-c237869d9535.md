# Cloud Saves on Convex — Architecture & Implementation Plan

## Goal
Replace SafeLauncher's folder-sync "cloud" (the watched `save_cloud.zip` directory) with real accounts + cloud storage on the existing Convex deployment `moonlit-sockeye-565` (project dir `~/Main/Programming/SafeLauncherDatabase`, currently empty). Limits: **10 MB max upload, 200 MB quota/user**, last 3 versions retained per game.

## Chosen stack (defaults applied; flagged where unverified)
- **Auth:** Clerk via its officially supported desktop pattern — system-browser OAuth2 Authorization Code + PKCE (S256) → loopback callback server on `127.0.0.1:<random port>` → token exchange at Clerk Frontend API. Access tokens are JWTs; Convex validates them through its auth pipeline.
- **Token→Convex wiring:** primary route = Convex `auth.config.ts` `customJwt` provider pointing at the Clerk instance domain/JWKS (`aud` must match the OAuth-application token's audience exactly). Early spike validates token shape (`aud`, `iss`, TTL) empirically; fallback = create a Clerk JWT template `convex` + native `clerkProvider`. This is the riskiest unknown and is validated first.
- **Storage:** Convex File Storage for save blobs (10 MB ≪ documented caps), encrypted client-side (AES-256-GCM, new dep `cryptography`). Per-user key generated once, stored in the Convex users table. This protects payloads even though storage download URLs are bearer-style links.
- **Retention:** newest 3 generations kept per game-server-side; older evicted automatically after successful upload (explicitly user-visible in UI).

## A) Backend repo: `~/Main/Programming/SafeLauncherDatabase`
Greenfield Convex TypeScript project scaffolded from scratch:

```
package.json / tsconfig.json        convex/
├─ schema.ts                        ├─ auth.config.ts   # customJwt→Clerk issuer+JWKS
├─ http.ts    (route table)         ├─ lib/limits.ts     # MAX_SAVE=10MiB, QUOTA=200MiB, KEEP=3
                                     ├─ saves/*.ts       # mutations/queries/actions below
```

Schema (`convex/schema.ts`), all tables `strictAuthProvider`-keyed by identity subject:
| table | fields |
|---|---|
| users | subject, createdAt, keyCiphertext, keyNonce, plan (v1 constant "free") |
| games | userId, nameKey (sanitized, same charset as local engine), latestMtime, totalBytes, [by userId+nameKey unique] |
| saves | gameId, version, storageId, sizeBytes(compressed+ciphertext blob size), plainSha256, sourceMaxMtime (manifest content clock), manifestSummary, createdAt |
| usageCounters | userId, uploadsToday, windowStart (lightweight abuse guard) |

HTTP actions (`https://moonlit-sockeye-565.convex.site/api/*`), every route requires a valid Bearer JWT resolved via `ctx.auth.getUserIdentity()` and scopes every read/write to that subject:
- `GET  /api/me` → account info, quota used/free, game count.
- `POST /api/games/{nameKey}/saves/init` → validates size≤10MB & quota headroom (current usage + new ≤ 200MB, else explicit error with numbers); mutation creates pending save row + `ctx.storage.generateUploadUrl()`; returns `{saveId, uploadUrl}` (URL expires 1h).
- `POST /api/games/{nameKey}/saves/{saveId}/confirm` → reads back actual stored object size from storage metadata (never trusts client-declared sizes), rejects oversize with deletion of the orphan, bumps version, evicts generations beyond newest 3 (deleting their blobs), updates game.latestMtime/quota aggregate. Idempotent on retry.
- `GET  /api/games` & `/api/games/{nameKey}/saves` → listings incl. stats to power conflict UI (sourceMaxMtime is the comparison clock we already standardize).
- `GET  /api/saves/{id}/download` → access-checked action **streams the blob back inline** (~≤10 MB < the documented 20 MiB httpAction response cap) so no bearer storage URL ever escapes the authenticated context.
- `DELETE /api/saves/{id}` (and implicit prune-on-upload).
Client-supplied timestamps are recorded as metadata only; ordering conflicts are resolved against the manifest's `source_max_mtime` content clock (already standardized locally).

## B) Desktop client changes (SafeLauncher)
New core modules; existing UX paths stay intact because they already run inside worker threads:

1. `core/cloud_backend.py` — `ConvexSaveBackend`: HTTPS-only via `requests.Session` (reuse conventions from steamgriddb/ludusavi_installer: timeouts everywhere, streamed temp-file downloads ≤10 MB cap, atomic rename). Methods mirroring today's engine verbs: `fetch_game_stats(nameKey)` returning the existing `SaveStats`, `upload(zip_bytes)`, `download(nameKey)->temp file path`, plus `delete/list/quota`. All responses mapped onto existing `SyncStatus`/`SaveStats` types so call sites don't fork logic.
2. `core/clerk_auth.py` — login/session lifecycle:
   - Spins a one-shot loopback HTTP listener (single request; closes after callback; validates `state`; PKCE verifier held in memory only).
   - Opens the system browser; user completes sign-in; token exchange mints `{access_token, refresh_token, expires_in, id_token}`.
   - Token store: `~/.local/share/safelauncher/auth.json` chmod **0600** in XDG dir created `0700` (matches existing perms conventions; refresh_token never logged, redacted from any diagnostics).
   - Proactive refresh ~30 s before expiry inside `authed_session()`, serializing refreshes behind a lock.
3. `core/save_crypto.py` — AES-256-GCM envelope: random per-user data key at first use (server stores wrapped copy + nonce alongside user row); payload format `[1-byte version][12-byte nonce][ciphertext][16-byte tag]`; plaintext zip written to temp file `0600` before `ZipBackupManager.import_save`.
4. Integration into sync flow — keep `CloudSaveSyncEngine` as the offline/local-folder engine and add thin dispatch in the same module-level API used by all four flows (pre-launch gate, exit auto-upload, properties dialog Sync Now buttons, SaveManagerDialog): when QSettings `cloud_mode == "convex"` and a session exists, upload/download/stats delegate to backend (archive bytes produced/consumed byte-compatibly via the same `ZipBackupManager.export_save_locations`/`import_save`, preserving manifest `source_max_mtime` semantics); otherwise fall back to current folder-sync behavior unchanged. Offline/expired-session errors degrade gracefully to local mode with a visible toast (no silent failure patterns).
5. UI additions:
   - Settings → Cloud tab gains "Account" section: Sign in (launches browser flow), email, quota bar (used/200 MB), logout, cloud-mode toggle (Local folder vs Convex account).
   - Small `LoginDialog` wrapper showing browser-launch status/instructions (system dialog affordances consistent with existing frameless style via DialogTitleBar).
6. `main.py` DI: construct backend/auth service once, pass into MainWindow (extending the existing ctor injection pattern minimally).

## C) Security controls (summary)
- Server: strict auth on every handler; ownership scoping by subject claim; size ceiling re-checked against stored object metadata post-upload; quota enforced transactionally in confirm mutation; upload URL issued only through the gated init mutation; downloads stream through auth checks (no public storage URLs exposed); JSON error bodies without internals.
- Client: PKCE+state, one-shot callback socket bound to 127.0.0.1, tokens at 0600 under 0700 dir, proactive single-flight refresh, secrets never logged, payload envelope encryption.
- Client-uploaded names pass through the same sanitization key as local engine to prevent collisions/traversal-style naming abuse.

## D) Reliability
Idempotent confirm (retry-safe after crash mid-upload via pending-row state machine: pending→confirmed/orphan-pruned); verifications off actual object metadata; atomic writes throughout reuse existing staged-file helpers; bandwidth-friendly (only changed games uploaded — content hash `plainSha256` lets pre-launch gate skip identical payloads); network failures surface as recoverable state (pending rows garbage-collected after 24h).

## E) Build/test sequence (validation gates ordered by risk)
1. **Spike (riskiest first):** manually mint a Clerk token, confirm `customJwt` provider accepts it via a hello-world httpAction. If fallback needed, pivot to JWT-template/clerkProvider before building anything else.
2. Backend: schema + http routes deployed to moonlit-sockeye-565 via `npx convex dev` then production deploy; smoke-test with curl scripts exercising happy-path + over-size + quota-exceeded + cross-user isolation.
3. Desktop: clerk_auth + backend + crypto modules with unit tests (PKCE verifier math, envelope round-trip, token refresh windowing) added to `test.py`.
4. Wire dispatch/QSettings/UI; end-to-end test against the dev deployment (login → upload → second-machine restore semantics → conflict dialog → quota accounting → retention eviction).
5. Docs: README/QUICKSTART update + `Dev.txt` notes; `.gitignore` for node_modules/.env; `.env.local` never committed (secrets list documented instead).

## F) Explicit non-goals / known limitations
- No sharing between different users' accounts (per-user namespace only).
- Convex free tier currently includes ~1 GB file storage + ~1 GB egress/mo — fine for personal use now, revisit pricing if many users adopt.
- Zero-knowledge option deferred (documented future path in save_crypto.py header).
